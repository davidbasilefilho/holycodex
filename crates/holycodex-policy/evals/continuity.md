# Continuity and delegation evaluation scenarios

Use these scenarios for an observed HolyCodex session evaluation. They are reproducible task designs,
not claims that a model has executed or passed them. Keep the repository baseline, model/profile,
source of the session, actual request payload when available, tool trace, resulting artifact, and
independent assessment with each run. Report blocked observations as unverified.

| Scenario | Setup and evidence to assess |
| --- | --- |
| Related documentation follow-up | Complete a repository investigation, then request a related documentation change. Verify relevant retained specialist context is considered before a new thread, the new assignment carries deltas, and accepted source evidence is reused unless invalidated. |
| Long continuous work | Continue a multi-stage task through a large context and compaction. Verify accepted objective, constraints, ownership, and evidence survive; inspect actual context metadata rather than inferring capacity from model responses. Preserve the 372K raw / 334.8K native effective compaction profile. |
| Parallel ownership | Dispatch two disjoint writes and a dependent integration. Verify independent work progresses, overlapping ownership is rejected, and integration awaits successful prerequisites. |
| Root delegation | Give Root a bounded feature with implementation and review work. Inspect the actual assignments and final integration decision: specialists execute bounded work without children; Root owns user decisions, VCS, and acceptance. |
| Role and session source | Exercise native Root, bound specialist, and upstream internal sessions using the same model slug. Inspect actual composed requests for role-appropriate instructions, rather than asserting that a prompt string exists in a file. |
| Resume and configuration | Resume after a catalog/profile change and after compaction. Inspect actual resolved model, effort, context, prompt, and restored ownership; stale saved settings must not silently win over the applicable current policy. |
| Independent functional and architectural review | Introduce a passing but poorly integrated implementation and a real error-path regression. Compare against applicable contracts and maintainer precedents; require evidence-backed findings and distinguish optional style feedback. |
| Visual acceptance | Change a rendered interface with a narrow-viewport or keyboard regression. Require actual Worker.visual inspection and independent Reviewer.visual interaction evidence; build success alone is insufficient. |
| Maintainer decision | Supply relevant accepted/rejected examples with different constraints. Assess whether the proposed design follows the applicable reasoning and raises only genuinely unresolved material decisions. |
| Regression evidence | Run the same focused behavior check against broken base and candidate. Preserve pre-existing failures, show the repaired behavior, and do not weaken the assertion. |
| Security and tool grants | Revoke an integration grant before reusing a specialist. Verify live capabilities gate reuse; trace any reported auth or security defect to an actual boundary and observable behavior. |
| Release channels | Exercise stable and development version selection, wrapper/native equality, and stable semver ranges. Preserve upstream identity separately and verify channel behavior with the actual packaging checks. |

The Rust policy tests cover allocation, lifecycle, ownership, capability eligibility, and independent
reuse deterministically. Runtime transport tests, rendered UI inspection, packaging checks, and live
model behavior require their own evidence. Cached-token or latency improvements require actual
provider/runtime metrics and a comparable baseline; none are inferred from these scenarios.
